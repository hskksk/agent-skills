# 日本語で書くときの作法

出力言語が日本語のときに読む。**必読**。

扱うのは文と語のレベルである。語の結びつき、修飾の距離、主述の対応、読点、語種のバランス。段落の順序や論証の骨格はここでは扱わない。

このファイルは二部構成になっている。第1部が**直訳調をやめる方法**、第2部が**日本語の文を整える方法**である。第1部を先に読む。読みにくさとして現れるのは、ほとんどが第1部の問題である。

---

# 第1部 直訳調をやめる

## 1.1 何が起きているか

英語の技術文書の言い回しを一語ずつ日本語に置き換えると、文法としては正しいのに、その分野の日本語として読んだことのない文ができる。読者は意味を取れるが、一拍余分にかかる。それが累積したものが「読みにくい」という感覚になる。

一文だけ見ると、たいてい「ちょっと変」で済む。レポート全体に百箇所あると、最後まで読めない文書になる。

```
NG: 辺が関係を運ぶ。
OK: 辺が関係を表す。

NG: 付録は本文を短くするために稼ぐ。
OK: 付録に回して本文を短くする。
```

直すときは、意味を保ったうえで**短い言い換え**を優先する。比喩の絵が成立しない語（運ぶ、稼ぐ、教えてくれる）だけを、説明的な長文に広げる必要はない。

## 1.2 検出のしかた

**その動詞を、無生物主語のまま、同じ分野の日本語記事で見た記憶があるか。** 思い出せないなら直訳である。

第二の手がかりは、**元の英語が浮かぶかどうか**である。「〜を運ぶ」を見て carry が浮かぶなら、それは訳文である。自分で日本語として考えたなら英語は浮かばない。

第三に、**その語を辞書的な意味で受け取ったとき、絵が成立するか**を見る。「辺が関係を運ぶ」は、辺が荷物を持って移動する絵になる。成立しないなら比喩が移植できていない。

### 直す強さの目安

全部を「和文だけの言い回し」に寄せる必要はない。次の三つに分ける。

1. **直す（絵が崩れる）** — 辞書の意味の比喩がそのまま残り、読者が一瞬止まる。短い言い換えで済むならそれを使う（表す、回す、示す、可能にする）。
2. **文脈で許容** — 英語起源でも、分野で定着している、または短い言い換えのほうが長くなる。直訳禁止の表より、読みやすさと分量で決める。
3. **そのままでよい** — すでに日本語の技術文で普通に見る形。無生物主語＋動詞の組み合わせが自然なら触らない。

「モデルは〜を知っている／理解している」のように、**モデル・エージェントを主体に扱う**書き方は、機械学習・生成 AI の文脈では読者に受け入れられている。無生物主語の例外として残してよい。データやログを「教えてくれる」主体にするのは、まだ 1 のほうが多い。

## 1.3 動詞の比喩 — 置き換え表

英語の技術文書で頻出する動詞の比喩である。**1 のとき**の短い言い換えの型。コピーではなく、同じ構図が出たら同様に直す。

### 直すことが多い（絵が崩れる）

| 英語 | 直訳（避ける） | 短く直すなら |
|---|---|---|
| X carries Y | X は Y を運ぶ | X が Y を表す／示す／担う |
| X earns its keep | X は稼ぐ | 付録に回す／〜のために置く |
| earn a pass | 通過を稼ぐ | 通過の根拠にする |
| X buys you Y | X は Y を買う | X で Y が得られる／省ける |
| buy back | 買い戻す | 取り戻す |
| make X honest | X を正直にする | 形式だけにしない |
| cosmetic | 化粧 | 見せかけ／名目だけ |
| wearing the wrong hat | 帽子を間違えた | 層を間違えた／置き場所が違う |
| count your breath | 一息を数える | 一息で読める長さに |
| hold only what is true | 真であるものだけを持つ | 〜だけを扱う |
| X tells us | X は教えてくれる | X から〜が分かる／X は〜を示す |
| the question is open | 問いは開かれている | 未解決である |
| X is not yet done | X は尚未完 | まだ書き終わっていない |

### 文脈で決める（定着・短さ）

| 英語 | 直訳 | コメント |
|---|---|---|
| surface area | 表面積 | 比喩の「表面積」は避ける。攻撃面・対象範囲・**サーフェス**など、分野の定着語を使う。言い換えが長くなるだけなら無理に和文にしない。 |
| parallel threads | 並行する糸 | ソフトウェアでは **並行スレッド**・**並行処理** が定着していることが多い。 |
| headings name things | 見出しは名付ける | **見出しで示す／名付ける** は許容。意味が曖昧なときだけ「対象を指す」に寄せる。 |
| X allows Y | X は Y を許す | API では **許可する**・**可能にする** が普通。「許す」単体の一人称比喩だけ避ける。 |
| X sees Y | X は Y を見る | 監視・検知では **検出する**・**捉える** が短いことが多い。定着した「見る」は残してよい。 |
| X is promising | X は有望だ | 何が使えるかを一行で書くほうが読みやすいときだけ具体化する。 |
| X knows Y | X は Y を知っている | **モデル・エージェント**の主語なら、多くの読者は自然と受け取る（上の目安）。ログ・データの主語では避ける。 |

### 1.8 でよく出るが、直訳でも許容されやすい語

次は英語起源だが、日本語の技術文で広く使われ、**無理に言い換えると長くなる**ことが多い。

- **〜を可能にする** — 〜できるようにする、と同程度で許容。
- **〜に寄与する** — 硬いが短い。毎回「役に立つ」にするとリズムが単調になるなら残す。
- **〜を実現する** — 名詞化の「実現」より、動詞の「実現する」は許容範囲が広い。

逆に、**〜において**・**〜に他ならない**・**重要なのは〜である**（空の強調）は、短く削れるので 1 に近い。

## 1.4 名詞を動詞に戻す

英語は動詞を名詞にして弱い動詞で支える。日本語に直訳すると「〜の〜を行う」「〜化をもたらす」という重い文になる。日本語では動詞のまま書く。

```
NG: レイヤ境界の明確化が品質事故の重大性を低下させる。
OK: 層の境界を決めておくと、品質事故が軽く済む。
```

危険な語尾は「〜化」「〜性」「〜の実施」「〜を行う」「〜をもたらす」である。連続したら名詞化を疑う。

ただし定着した術語は名詞のままでよい。「正規化」「冪等性」「可観測性」は、その分野がその形で使っている。置き換えるのは、書き手がその場で作った名詞である。

## 1.5 複合語を勝手に作らない

英語は名詞を並べるだけで複合語になる。日本語は助詞か、定着した熟語が必要である。

```
NG: 品質表面積が増える。
OK: 品質保証の対象が広がる。

NG: コスト関数の再最適化として提示されている。
OK: 損得を計算し直した結果として書かれている。
```

数式でないものを「不等式」「関数」と呼ばない。比喩として持ち込むと、読者はそこに数式があると思って探しに戻る。

## 1.6 「持つ」の乱用をやめる

英語の have / has をそのまま「持つ」にすると、日本語として不自然な箇所が大量に出る。

```
NG: このレポートは著者を持たない。
OK: このレポートは、書いた人の説明なしで読める。

NG: 各節は同じ四つの契約を持つ。
OK: どの節も次の四つを守る。
```

プログラミングの **クラスがメソッドを持つ**・**API がフィールドを持つ** は定着している。直すのは、レポートや説明文で have を機械的に「持つ」にしたときの不自然な箇所に限る。

## 1.7 無生物主語の扱い

日本語は無生物主語を取れるが、取れる動詞が英語より狭い。「示す」「表す」「決まる」「増える」なら自然で、「教える」「望む」はデータやログの主語では不自然になりやすい。

```
NG: データが教えてくれるのは、欠測が集中していることである。
OK: 欠測は特定の期間に集中している。
```

**モデル・エージェント**を主語にした「知る」「理解する」「学習する」は、生成 AI の読者には自然なことが多い。直す必要があるのは、比喩が崩れる動詞（教えてくれる、稼ぐ、運ぶ）や、出力の性質を説明したほうが明確なときだけである。

```
許容: このモデルは文脈を理解している。
直す: データが教えてくれるのは、欠測が多いことだ。
```

無生物主語が続いて重くなったら、「〜によって」「〜では」「〜すると」に開く。ただし「〜を可能にする」だけを短くするために文を壊す必要はない。

```
重い: 比較表は、共通点と例外の識別を可能にする。
軽い: 比較表で共通点と例外を区別できる。
```

## 1.8 定型の訳文

英語のレポート定型をそのまま日本語にすると、意味は通るが**枠だけ**が残って内容が空洞になることがある。置き換え先も、別のメタ語にすり替わっているだけのことが多い。扱いは三つ——**削る**、**内容を先に書く**、**短い言い換え**——に分ける。

### まず削るか、内容に置き換える

| 訳文・定型 | 何が弱いか | どうするか |
|---|---|---|
| 重要なのは〜である | 強調の空枠。後ろが同じでも「重要」が増えるだけ | 削る。重要なら段落の先頭・見出し・太字で示す |
| 〜に他ならない | 英語の rhetoric の残り | 削る。言いたいことをそのまま書く |
| 〜という観点から | 視点の宣言で、論がまだ始まっていない | 削る。必要なら「〜では」で主題を立ててから述べる |
| 〜において | 多くは冗長。「において検討する」は二重の枠 | 削る。残すなら「〜では」「〜に関して」程度。安易に「〜の場合」にしない |
| 本稿は〜を調査する／三つの主張に整理する | 手順の宣言。読者は結果が欲しい | 削る。最初の文から論点・結論・具体に入る |
| この節が〜へ足すのは | 「足す」比喩＋メタ | 削る。追加する内容をそのまま書く |
| 〜と言えるだろう | 責任の先送り | 根拠があるなら言い切る。なければ「未確認」「〜までは言えない」 |

```
NG: 重要なのは、境界を決めることである。
OK: 境界を決めないと、再実行で履歴が重複する。

NG: この節は比較の観点から、三代の違いに足す。
OK: 三代の違いは、次の三つに集約できる。

NG: 本稿は関連文献を調査し、五つの論点に整理する。
OK: （最初の文から五つの論点の一つ目、または結論）
```

### 比喩・借り語——直訳も置き換えも疑う

| 訳文 | 直訳・よくある置き換えの弱点 | 向きのある言い方 |
|---|---|---|
| 読者が持ち帰るもの | 「持ち帰る」は英語の take-away。「残る理解」も抽象で枠が残る | **枠を捨てて書く**。「ここでの結論は〜」「判断するときは〜を見る」 |
| 概念の借用 | 「考え方だけを取り入れる」は説明的で長い | **〜の考え方を採用する**／**〜から着想を得る**。学術調なら **〜を借用する** も可 |
| 手法の去就 | 「続けるかどうか」は口語寄り。去就自体は漢語だが英語 fate の訳で浮く | **採用を続けるか**／**やめるか**／**置き換えるか**と、選択肢を具体語で書く |
| 肩代わりしない／代わりにはならない | どちらも比喩が残る | **〜に取って代わるものではない**／**〜を省略する理由にはならない** |

```
NG: 読者が持ち帰るものは、検証の手順である。
OK: 検証は、再実行前にスキーマとソルトを揃える。

NG: 概念の借用として、グラフ理論を持ち込む。
OK: グラフの辺とノードの考え方を、そのままデータモデルに当てはめる。

NG: このチェックリストは設計レビューの肩代わりにならない。
OK: チェックリストがあっても、設計レビューは省略できない。
```

### そのままでよいことが多い（無理に和文にしない）

| 定型 | コメント |
|---|---|
| 〜を可能にする | 技術文で普通。冗長なら「〜できる」に寄せる |
| 〜に寄与する | 硬いが短い。言い換えが長くなるだけなら残す |
| 〜を実現する | 名詞の「実現」より動詞は許容範囲が広い |

### 置き換え表の落とし穴

- **メタ語を別のメタ語にする** — 「持ち帰る」→「残る理解」、「足す」→「見えるようになる」は、読者の手が止まる点が変わらない。
- **「〜の場合」を万能にする** — 「において」の代わりに増やすと、かえってぼんやりする。
- **「ここでは〜を扱う」** — 本稿は〜を調査するの置き換えとして使いがちだが、まだ宣言文。一行で済むなら目的だけ（「目的は〜だ」）、長いなら最初の文から入る。

## 1.9 制作メタを読者向け本文に出さない

執筆・編集のための語（「骨格」「スロット」「この節の役割は」など）を、読者向けの見出しや本文にそのまま載せない。読者は制作過程を知らない。見出しは、その節で分かることや探せる対象の語で書く。

# 第2部 日本語の文を整える

## 2.1 修飾語は係り先の近くに置く

日本語は修飾語を係り先からいくらでも離せる。離した分だけ、読者は係り先が現れるまでその修飾語を覚えておくことになる。読みにくい日本語のほとんどがこれである。覚えておくものが多すぎるか、覚えておく時間が長すぎる。

```
NG: 僕は山本が佐藤が受賞したと電話したのかと思った。
OK: 佐藤が受賞したと山本が電話したのかと僕は思った。
```

語はひとつも削っていない。入れ子をほどいて、次の修飾が始まる前に前の修飾が終わるようにしただけである。以下の規則はすべてここから出る。迷ったらここに戻る。

### 長い修飾語を前に

ひとつの係り先に修飾語が複数かかるときは、長いものを前に、短いものを後ろに置く。

```
OK: 十年前に読んだ古びた厚い本
NG: 厚い古びた十年前に読んだ本
```

短い修飾語を先頭に置くと、その後ろに続くすべてが、その修飾語と係り先の間に挟まる。

### 節を先に、句を後に

```
NG: Raw Vault は監査のために挿入のみで履歴を保持する層である。
OK: Raw Vault は、監査のために履歴を残す層であり、挿入のみで運用する。
```

### 主語を前に出すかどうか

主語を機械的に文頭へ出す規則は要らない。効くのは**主語と述語の距離が縮むとき**だけである。

```
NG: ソースの追加に対する耐性を得るために採用される Hub と Link の分離は、
    運用コストの大半を決める。
OK: Hub と Link を分けるのは、ソースの追加に強くするためであり、
    この設計が運用コストの大半を決める。
```

リサーチレポートに人称主語はほとんど出ないので、「私は」を反射で足す癖より、長い修飾を前に出す操作のほうが効く。

## 2.2 主述のねじれ

長い文は途中で主題を見失う。述語が文頭の主題と対応しないまま終わる。読者は違和感だけを覚えて、どこが変なのかは指摘できない。

見つけ方は、修飾語をすべて取り払って残りを読む。

```
NG:  このアプリの特徴は、誰でも簡単に画像が編集できます。
     → 特徴は、編集できます。    ← 「特徴」は「編集」できない
```

直し方は2通りある。どちらでもよい。

```
述語を名詞にする: このアプリの特徴は、誰でも簡単に画像を編集できることである。
主題を変える:     このアプリでは、誰でも簡単に画像を編集できる。
```

レポートで実際に出た形。

```
NG: 今回の整理としては、本質と事故を分けることで理解が進みました。
OK: 本質と事故を分けると、理解が進む。

NG: 運用記事の半分は、SQLよりもトレーニング計画と合意形成の失敗談である。
OK: 運用記事の半分は、SQLではなくトレーニング計画と合意形成の失敗を書いている。
```

長さが警告になる。主題と述語を同時に視野に入れられない長さの文を書いたら、他を確かめる前に切る。

## 2.3 「は」と「が」

節の第一文では、その節が扱う**主題**を明確にする。発見を示す節なら、主題を「は」で立てる。

```
弱い: Raw Vault を BI に直結しない運用が、公開事例で最も一貫して推される。
    ← 「が」で始めると、新情報の提示になり、主張として立たない
強い: Raw Vault は BI から直接読ませない。これが公開事例で最も一貫している境界である。
```

目安はこうである。すでに話題になっているもの、これから論じるものは「は」。初めて出すもの、その文で新しく特定するものは「が」。

対比を作るときは「は」を二つ並べる。

```
OK: Raw Vault は監査のため、情報マートは読みやすさのために存在する。
```

## 2.4 読点

用途は4つ、禁止がひとつ。

1. **節と句の切れ目に打つ** — これが既定。構造を伝える読点である。
2. **語順で直せないときに打つ** — どこで区切って読むかを示す。
3. **強調のために打つ** — 「私は、勉強ができるだけでも素晴らしいと思う。」は「私は」を対比として立てる。
4. **それ以上は打たない** — 境目すべてに打つと、読点の信号が消える。

用途2と3では、**まず語順を直し、直せないときだけ読点で救う**。読点で救った文は、たいてい語順でも直せる。

文中で項目を並べるときは、読点ではなく中黒を使う。構造を示す読点と、列挙を視覚的に区別できる。

```
NG: 列順、NULL処理、ソルトを揃えないと、JOIN が成立しなくなる。
OK: 列順・NULL処理・ソルトを揃えないと、JOIN が成立しなくなる。
```

## 2.5 語種のバランス

漢語だけでつなぐと硬く、和語だけだと締まらない。**コンピュータサイエンスやソフトウェア工学の文脈では、カタカナ語・英語略語・漢語の術語がそのまま標準語**である。直すのは、術語を和語に戻すことではなく、**書き手がその場で積み上げた名詞の塊**と、**つなぎの文を官公庁調にした部分**である。

### 触らなくてよい（CS で普通）

次は和語・別のカタカナに置き換えない。意味がずれるか、読者が英語文献と対応づけられなくなる。

- **実装・運用の語** — コミット、プッシュ、マージ、デプロイ、リリース、ロールバック、ビルド、キャッシュ、バッファ、キュー、スレッド、プロセス、スケジューラ、ガベージコレクション
- **構成・データの語** — API、スキーマ、インデックス、トランザクション、レプリケーション、シャーディング、正規化、冪等性、可観測性、スループット、レイテンシ
- **インフラの語** — キャパシティ（処理能力・台数の意味）、パイプライン、クラスタ、オーケストレーション、ヘルスチェック
- **固有名・製品の語** — Hub・Link・Satellite（Data Vault）、Raw Vault、特定製品名

「コミット」を「引き受ける」、「キャパシティ」を常に「余力」にするのは**誤り**である。Git のコミットと、約束を引き受けることは別語。キャパシティはサーバやスループットの話で、組織の余力とは別のことが多い。

### 和語に開くのはつなぎと、作った名詞化

```
硬い: 層間境界の明確化は品質事故の重大性低減に寄与する。
自然: 層の境界を決めておくと、品質事故が軽く済む。
```

上の「硬い」文で問題なのは、**境界・明確化・重大性・低減**の名詞化の連鎖であり、「寄与する」や「層」そのものではない。定着した術語（可用性、スループット、レイテンシ）は、無理に「使える時間」「遅れ」だけにしない。

```
硬い: 当該手法の継続的運用には相当規模の人的資源投入が要求される。
自然: この手法を続けるには、それなりの人数が必要である。
```

**当該**・**人的資源投入**・**要求される**は、論文・公文の借り文。技術ブログや設計メモでは、主語と述語を短くする。

### 漢語が続くときの数え方

「漢語が三つ続いたら一つ開く」は、**術語の複合**には当てない。

| 数える（つなぎが硬い） | 数えない（CS の定型） |
|---|---|
| 品質事故の重大性低減 | データベースのトランザクション分離 |
| 実装における複雑性増大 | 分散トレーシングのサンプリング率 |
| 運用プロセスの効率化推進 | メモリリークのガベージコレクション |

迷ったら、**その分野の日本語ドキュメント（公式ドキュメント、国内の技術記事）で同じ概念を何と呼んでいるか**を基準にする。英語を知っている読者向けの文では、カタカナ・英語表記のままのほうが短く正確なことが多い。

### カタカナ・英語を和語にするのは「比喩の英語」だけ

次のような**英語の比喩・ビジネス動詞**は、和語や短い動詞に寄せる余地がある（1.3 と重なる）。

| 英語の比喩・口語 | CS では置き換えやすい |
|---|---|
| drive adoption / drive the rollout | 普及を進める／展開を進める（**ドライブする**単体は避ける） |
| buy-in（合意の比喩） | 合意を得る／関係者の賛同 |
| leverage X | X を使う／X に載せる（**レバレッジ**単体は避ける） |

同じ語形でも、**Git の commit** はコミットのまま、**commit to a plan** は「計画を確定する」など文脈で分ける。

### カタカナ語の濁り

定着していないカタカナは、音だけ借りて意味がぼやける語である。**サインオフ、オンボーディング、ハンズオン**など、文脈で日本語が短いなら和語を選ぶ。一方、**デプロイ、マイグレーション、リファクタリング**は、CS 文脈では和語に戻す必要はない。

## 2.6 文のレベルの習慣

**短く切って言い切る。** 長い複文は、それぞれが終わる複数の文になる。音読して息が続かない箇所には句点が足りない。ただし短ければ良いわけではない。ひとつの考えに条件が付いているだけの文は、120字あってもひと続きで読める。分けるべきなのは、独立した主張がふたつ入っている文である。

**常体で統一する。** 既定は「〜である」「〜した」「〜ない」。文末に「です」「ます」を使わない。指定があったときだけ敬体にする。

**同じ語を一文のなかで繰り返さない。**

```
NG: 三分割で文章を書く方法は、小学校で文章を書くときから、企業の広告用の文章を書くときまで、幅広く使える。
OK: 三分割で書く方法は、小学校の作文から企業の広告まで幅広く使える。
```

**逆接の「が」は一文に一度まで。** 「〜だが、〜が、〜である」は、どちらの「が」で論が折り返すのかを読者に考えさせる。文を分ける。

**代名詞を避ける。** 数節前のものを「それ」「これ」で受けると、読者は指示先を探して戻る。名詞を繰り返すか、構造を変える。

**「〜的」「〜性」を重ねない。** 「構造的な複雑性の本質的な特性」は何も言っていない。具体語に落とす。

**二重否定を避ける。** 「〜でないとは言えない」は「〜の可能性がある」と書く。

**受身を続けない。** 「〜されている」が三文続いたら、行為者を主語に戻せる文がある。

**体言止めは表と箇条書きだけ。** 散文では文にする。見出しは名詞句でよい。

**読者が別の意味に取りうる語は、それが効く文で定義し直す。** 日常語と重なる術語（「複雑さ」「単純」「品質」「継続率」）はとくに危ない。

**入門読者には、名前より先に動作を書く。** 未知の術語を別の未知の術語で説明しない。まず何が起きるか、従来は何に困ったかを平易に書き、その現象や仕組みの名前として術語を置く。TL;DRに出した語も、本文では初出として扱う。

### 簡潔にする順序

簡潔さは、文を短く切ることではない。読者が意味を取るまでの手順を減らすことである。初稿を書いたあと、次の順で直す。

1. **結論を先に出す。** 「〜を検討すると」「〜という観点では」から始めず、何が起きるかを書く。
2. **一文を一つの主張にする。** 条件・主張・例がそれぞれ独立して読めるなら分ける。
3. **名詞を動詞へ戻す。** 「重要性が増大する」は「重要になる」、「改善を実現する」は「改善する」と書く。
4. **同じ内容を一度だけ書く。** 言い換えて繰り返さない。段落末の要約も、新しい区別を加えないなら削る。
5. **なくても意味が変わらない語を削る。** 「基本的に」「実際に」「非常に」「〜ということ」は、条件や強さを変えない限り要らない。

```
長い: この方式を採用することによって、更新処理の実行時における競合の発生を抑制することが可能になる。
短い: この方式なら、更新時の競合を減らせる。

曖昧: この区別には運用上の重要性がある。
具体的: この二つを混ぜると、再実行で履歴が重複する。

詰め込み: キャッシュは応答を速くするが、無効化が遅れると古い値を返すため、更新頻度が高い画面ではTTLを短くする必要がある。
分ける: キャッシュは応答を速くする。一方、無効化が遅れると古い値を返す。更新頻度が高い画面では、TTLを短くする必要がある。
```

短くして主語や条件が消えるなら、削りすぎである。短文を並べるだけで関係が見えなくなった場合は、「一方」「そのため」などでつなぐ。

## 2.7 段落の頭の接続表現

関係が自明でない段落は、つながりの語で始める。

| つながり方 | 段落頭に置く表現 |
|---|---|
| 順接・帰結 | したがって / そのため / この結果 |
| 逆接・対比 | 一方 / これに対して / ところが |
| 限定・留保 | ただし / とはいえ / この点は |
| 追加・並列 | さらに / 加えて / 同様に |
| 転換 | ここまでは〜だった。次に / 話題を変えると |
| 具体化 | 具体的には / たとえば |
| 言い換え | つまり / 言い換えると |

同じ表現を連続する段落で繰り返さない。とくに「さらに」の連打は埋め草になりやすい。関係が自明な段落には置かなくてよい。

## 2.8 文中に値を並べない

値の並びを地の文に置くと読めない。読者は比較相手が出てくるまで各数値を覚えておくことになる。

```
NG: ハッシュの性能は、MD5 の CHAR(32) で TEMP が最大、RAW(16) で中程度、
    数値サロゲートで最小となる。
OK: 表にする（表現形式 / TEMP 使用量 / 出典）
```

散文は論を書き、表は値を並べる。日本語では、読点で区切った値の列が節構造を示す読点と衝突するため、表に移す閾値が英語より低い。

## 2.9 英数字の表記

技術文の一般的な慣習に合わせる。

- 固有名・論文題・API 名・ファイルパス・コマンドは原文のまま。訳さない
- 和文と英数字の間に半角スペースを入れる。「Raw Vault は」「2026 年」ではなく「2026年」（年月日は詰める）
- 数字は半角。単位も半角
- 括弧は、中身が和文なら全角（）、英数字だけなら半角 ()

## 2.10 太字の使い方

日本語には大文字も語間の空白もない。斜め読みの手がかりは太字・リンク・数字・記号しかないので、**太字は装飾ではなく構造である**。個数の上限は設けない。代わりに、太字にするものを3種に限る。

1. 初出の術語
2. 数値と条件
3. 読み飛ばしてほしくない結果・条件・持ち帰り

この3種以外に使わない。感想や強調のために太くしない。目安は本文1,000字あたり3〜8箇所で、それを下回ると灰色の帯になる。
