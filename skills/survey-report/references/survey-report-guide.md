# 調査レポートの型の選択と出力ガイド

調査（リサーチ）は、知識の獲得段階に応じて **「Phase 1: 探索型（景観・論点の特定）」** と **「Phase 2: 検証・構造化型（答え・根拠の構築）」** の2つの局面に分かれます。

本ガイドでは、依頼文からレポート型を選ぶ**判定ルール（Phase）**、読者にどう情報を見せるかを決める**重心**、どこから説明を始めるかを決める**読者レベル**を定義します。**Phase は「問いの確定度」、重心と読者レベルは「情報設計」であり、独立した軸です。**

---

## 1. 依頼内容からのレポート型自動判定ルール（Phase ルーティング）

依頼文に含まれる「問いの具体性」「読者の目的」「前提の有無」から、適用すべきレポート型を判定します。

```
[ユーザーからの依頼文を入力]
           │
           ▼
  具体論点・仮説はあるか？
   ├── YES ──> 【Phase 2: 検証・構造化型レポート】
   └── NO  ──>  全体像や最新動向の把握が目的か？
                 ├── YES ──> 【Phase 1: 探索型レポート】
                 └── 曖昧 ─> 【Phase 1 で発信（末尾で Phase 2 用の問いを提示）】
```

### 判定基準と具体例

| 評価項目 | Phase 1: 探索型レポート（Landscape & Issue） | Phase 2: 検証・構造化型レポート（Solution & Proof） |
|---|---|---|
| **依頼の特徴** | 広範なテーマ、全体像の把握、トレンド調査、未知分野のキャッチアップ | 特定の選択肢比較、要因分析、仮説検証、意思決定のための判断材料 |
| **問いの具体性** | 「何が問題か」「今どうなっているか」が未特定 | 「AとBどちらを選ぶべきか」「なぜ事故が起きたか」など具体的 |
| **発話パターン** | ・「〜の全体像を調べてほしい」<br>・「〜に関する最新動向や主要論点は？」<br>・「〜について基本から概観したい」 | ・「〜と〜のトレードオフを比較検証して」<br>・「〜のボトルネックとその解決策を示して」<br>・「〜を導入すべきか根拠をまとめて」 |
| **出力のゴール** | 読者に**地図**を示し、**次に解くべき3つの問い**を提示する | 読者に**結論**を示し、それを支える**論理と根拠**を展開する |

※ どちらか判断がつかない・境界にある場合は、まず **Phase 1（探索型）** としてレポートを作成し、冒頭および本文末尾で「次に深掘りすべき問い」を明示して読者と合意形成を行います。

---

## 2. 三つの軸の関係（Phase × 重心 × 読者レベル）

Phase を決めたら、**書く前に `gravity.md` を読み**、次の二つを別々に決めます。詳細とテストは `gravity.md` が正本です。

| 軸 | 何を決めるか | 選択肢 |
|---|---|---|
| **Phase** | 問いの確定度とレポートのゴール | Phase 1（探索）/ Phase 2（検証） |
| **重心** | 読者が時間を使う**価値の中心**と情報配置 | 前重心 / 中重心 / 後重心（副重心は一つまで） |
| **読者レベル** | どこから説明を始めるか | 入門 / 実務 / 専門（指定がなければ入門） |

**軸は独立です。** 前重心だから専門家向け、Phase 1 だから後重心、といった対応はありません。

- **Phase 1** は地形の比較・分類が中心になるため **中重心**が自然です。全体像だけを素早く把握したいなら前重心、既存の言説を検証して問いを立て直すなら後重心も選べます。**地図と「次に解くべき3つの問い」はどの重心でも残します。**
- **Phase 2** は依頼の目的で選びます。判断を急ぐなら**前重心**、選択肢比較なら**中重心**、根拠の検証・追試なら**後重心**。**答え（一文）と根拠の対応はどの重心でも残します。**

どの重心でも、タイトル直後に3〜5項目の `## TL;DR` を置きます。長さの上限（例: 本文2万字程度）や検索回数を一律の規則にせず、レポートの目的に必要な構成と調査量を決めます。**調査の薄さは字数では測らず、互いに異なる資料・一次資料の比率・反対資料の有無で判断します。**

## 3. レポート型の特徴と見出し設計の比較

| 項目 | Phase 1: 探索型レポート | Phase 2: 検証・構造化型レポート |
|---|---|---|
| **出発点** | 問いや論点が未定、景観が不透明 | 問い・論点・仮説が定義済み |
| **見出しの性質** | **構造・対立軸を示す分類見出し**<br>(例: `## 2. 処理方式の対立: Stream型 vs Batch型`) | **主張・結論を示す言い切り見出し**<br>(例: `## 2. リアルタイム処理にはStream型を採用する`) |
| **中心成果物** | ドメインマップ、対立軸整理、抽出された問い | 結論の一文、根拠の展開、限界 |

見出しは `gravity.md` の階層ルール（`##` は読み方の切り替わり、`###` は具体的な発見・問い・比較対象）にも従います。

---

## 4. Phase 1: 探索型レポートの構造（景観・論点特定型）

問いがまだ定まっていない初期段階の調査であっても、単なる素材集めや百科事典にせず、**「全体像（マップ）」と「解くべき問い」を提示する完成されたレポート**として出力します。以下の節立ては既定案であり、重心に合わせて取捨・並べ替えます。**必須の成果物は「全体像」と「次に解くべき3つの問い」です。**

### 構成要素（既定案）

1. **`## TL;DR`**
   * 主要な結論と条件を一項目一文で3〜5項目。

2. **`## 概要`（L1 概要と主要な問い）**
   * テーマの背景と現状の要約（2〜3文）。
   * 現状の主要な対立軸や構造的課題（1〜2文）。
   * **「今後、優先して検証・解明すべき3つの問い（Issues）」**（箇条書きで明記）。
   * 調査範囲・対象資料（1文）。

3. **`## 全体像`（ドメインマップ / トピック構造図）**
   * 主要要素、技術、プレイヤー、対立軸の関係性。図は関係が明確になる場合だけ置く（Mermaid など）。

4. **`## 1. 背景・歴史 — <潮流の要約>`**
   * なぜこのテーマが現在注目・議論されているのかの文脈。中重心では比較軸の説明に必要な分だけ。

5. **`## 2. <概念・アプローチの対立軸>`（L2 本文: 分類・構造化）**
   * 単なる用語解説ではなく、「対立軸（A方式 vs B方式）」「トレードオフ」「ボトルネック」の切り口で構造化して記述。

6. **`## 3. 抽出された「重要な問い」の深掘り`**
   * **問い 1**: なぜ重要か、想定される仮説の選択肢。
   * **問い 2**: 調査を阻むボトルネック・未解決点。
   * **問い 3**: Phase 2で検証すべき具体的テーマ。

7. **`## まとめ — 次のPhase 2に向けた推奨アクション`**
   * どの問いから着手すべきかの優先順位の提言（ユーザーが求め、調査が支える場合）。

8. **`## 付録: 出典一覧`（L3 付録）**
   * `[n]` に対応する一次資料・データ・補足。採用しなかった調査の枝も残す。

---

## 5. Phase 2: 検証・構造化型レポートの構造（解・根拠構築型）

問いや仮説が定まった後のレポートです。`report-structure-guide.md` の「答えと根拠の対応」に準拠し、重心と読者レベルは `gravity.md` で決めます。

### 構成要素（既定案）

1. **`## TL;DR`**
   * 主要な結論と条件を一項目一文で3〜5項目。

2. **`## 概要`（L1 答えと位置づけの提示）**
   * 答え（一文）＋ 判断の軸 ＋ 位置づけ ＋ 調査範囲。主張の数は固定せず、重心に合わせる。

3. **`## 全体像`（論理構造図）**
   * 問い → 軸 → 分かったこと（主張） → 答え をつなぐ図。関係が明確になる場合だけ置く。

4. **`## 背景・歴史 — <経緯の主張>`**
   * 主張が成立するに至った文脈・歴史的経緯。後重心では成立過程が本文の中核になりうる。

5. **`## <番号>. <対象名詞> — <主張の要約>`（L2 本文: 主張型見出し）**
   * 見出し自体が結論になっている章立て（例: `## 2. 消費層は必須 — Raw VaultをBIに直結しない`）。

6. **`## まとめ — 要点リスト`**
   * 読者が持ち帰るべき決定事項・主張の要約。冒頭の言い換えにしない。

7. **`## 付録: 出典一覧`（L3 付録）**
   * `[n]` に対応する一次資料、データ、補足解析。採用しなかった調査の枝も残す。

---

## 6. 実務でのレポート連携フロー

実務・プロジェクトでは、依頼者との対話を通じて Phase 1 から Phase 2 へとレポートを進化させます。

```
[調査依頼を受領]
    │
    ▼ （Phase ルーティング → gravity.md で重心・読者レベルを決定）
    │
    ├──【パターンA: 目的・問いが曖昧】
    │      │
    │      ▼
    │   【Phase 1 レポート発行】
    │   ・全体像のマップと「解くべき3つの問い（A, B, C）」を提示
    │      │
    │      ▼（読者・上司と合意形成: 「問いAを検証しよう」）
    │
    └──【パターンB: 問い・選択肢が明確】
           │
           ▼
        【Phase 2 レポート発行】
        ・「問いAに対する答えはXである。根拠は以下のとおり」を提示
        ・意思決定・行動へつなげる
```

---

## 7. 提出前チェック

出力の直前に `checklists.md` の共通テストと、選んだ重心の重心別テスト、Phase 別テストを行います。数えられる指標は `measure.py` で確認し、**数字を手で書き換えない。**
